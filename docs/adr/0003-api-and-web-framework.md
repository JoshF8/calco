# ADR-0003 — API protocol and web framework

- **Status:** Accepted
- **Date:** 2026-05-24
- **Decision driver:** [@JoshF8](https://github.com/JoshF8)

## Context

With the backend language fixed to Go ([ADR-0002](./0002-backend-language.md)) and the frontend to TypeScript, the client–server protocol cannot use TypeScript-only RPC frameworks (tRPC, oRPC) without manual codegen workarounds.

We also need:

1. **Type safety on the frontend.** The TS client should know the shape of every request and response.
2. **A documented, standard contract.** The hosted SaaS version may expose a public API to enterprise customers (CI/CD integration, terraform-style workflows). The future CLI (`calco import`, `calco apply`) needs to consume the same API.
3. **A web framework in Go** that does not require us to hand-write OpenAPI YAML or annotate every route with comments.
4. **`net/http` compatibility** so the rest of the Go ecosystem (OpenTelemetry, structured logging, graceful shutdown patterns) plugs in without friction.

## Decision

**REST + OpenAPI 3.1** as the API protocol.

**Huma v2** as the framework that generates the OpenAPI spec from typed Go handlers, mounted on **chi v5** as the underlying router.

TypeScript types on the frontend are generated by **`openapi-typescript`** running against the spec exposed at `/openapi.json`.

```
apps/server (Go)        ──>  Huma v2 + chi v5  ──>  exposes /openapi.json
                                                          │
apps/web (TS)           <──  openapi-typescript reads spec, generates src/lib/types.gen.ts
```

## Consequences

### Positive

- **One API contract, many consumers.** Frontend, future CLI, future public API customers all consume the same OpenAPI document.
- **Type safety end-to-end** without TypeScript on the backend. Generated TS types catch breaking changes in CI.
- **Huma is router-agnostic.** If chi is later replaced by gin, gorilla, or a future option, the Huma layer is unaffected.
- **Production-proven.** Huma is used at scale by enterprise teams (live streaming video, others with millions of users).
- **OpenAPI is portable.** Tooling, monitoring, mocking, fuzzing — most of the API ecosystem speaks OpenAPI.

### Negative

- **More setup ceremony** than tRPC. Each route declares input/output structs and registers with `huma.Register`. Boilerplate is small but non-zero compared to a magical RPC layer.
- **OpenAPI spec drift risk.** If hand-written documentation diverges from generated handlers, consumers see stale shapes. Mitigated by treating `/openapi.json` (generated) as the only source.
- **Codegen step required** in the frontend pipeline. `openapi-typescript` runs on every build; CI must enforce it.

## Alternatives considered

### tRPC

Excellent DX for TypeScript-to-TypeScript apps; eliminates codegen entirely. **Rejected** because:

- TypeScript-only. The backend is Go (ADR-0002), so tRPC's central value proposition does not apply.
- No native OpenAPI output (the `trpc-to-openapi` adapter is unofficial and archived).
- The future CLI written in Go and any non-TS consumers would have to reverse-engineer a non-standard protocol.

### Hono with `@hono/zod-openapi`

Hono is a modern Go-adjacent TypeScript framework with OpenAPI generation. **Not applicable** because Hono is Node/Bun/Edge runtime, not Go. Included here only because it surfaced during early exploration before the Go decision was finalised.

### oRPC

Newer 2024–2026 contender combining tRPC's DX with OpenAPI output. **Rejected** for the same reasons as tRPC: TypeScript-only on the server side.

### Plain `net/http` + hand-written OpenAPI YAML

The pre-2023 approach. **Rejected.** Two sources of truth (handlers and YAML) diverge in practice. Tools like `swaggo/swag` add comments-as-spec which is fragile and unidiomatic in Go.

### Fuego

Go framework that generates OpenAPI from generics, similar idea to Huma but as a full framework rather than a router-agnostic layer. **Rejected** based on maturity and ecosystem size — Huma has substantially more production usage and a longer track record. Fuego is promising and may merit reconsideration if Huma stagnates.

### Fiber, Gin, Echo

Mainstream Go web frameworks. **Rejected** because none has first-class OpenAPI generation; all require external tools (`swaggo`, manual YAML, codegen wrappers) which reintroduce the dual-source-of-truth problem. Fiber additionally breaks `net/http` compatibility by using `fasthttp`, sacrificing middleware ecosystem for marginal speed wins.

### gRPC + gRPC-Web

Type-safe via protobuf, well-supported in Go. **Rejected** because:

- Browser support requires gRPC-Web proxy or Connect, adding operational complexity.
- The HTTP/JSON layer customers expect for a public API would need to be added separately.
- REST + OpenAPI achieves the same goals with one protocol and broader tooling.

## Risks

- **OpenAPI spec quality depends on Huma metadata.** If route registrations omit `Summary`, `Tags`, `OperationID`, generated TS types still work, but the public API documentation looks unprofessional. Linter enforced in CI (`huma lint`).
- **Future migration to gRPC for internal services** remains possible because REST + OpenAPI does not preclude adding gRPC alongside.
